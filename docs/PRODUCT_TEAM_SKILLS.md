# 产研团队 Skill 使用手册

> 这套 Skill 是一个由 4 个 AI 角色组成的**产研协作小队**，帮助你把一个模糊的想法，变成有文档、有设计、有代码、有验收的完整功能。

---

## 一、这套 Skill 是做什么的

平时开发一个功能，需要经历「想清楚需求 → 设计页面 → 写代码 → 验收测试」这几个步骤。

这套 Skill 就是为了让这个过程更顺畅：

- 你不需要一次性想清楚所有细节
- 每个角色都有明确的职责，不会乱串
- 每个阶段都有标准的输出，方便传递和追溯
- 有人帮你把关每个环节，防止遗漏和跑偏

---

## 二、四个角色分别是谁

| 角色 | 昵称 | Skill 名称 | 一句话职责 |
|------|------|-----------|-----------|
| 产品负责人 | 乔布斯 | `jobs-product-owner` | 理解需求，整理文档，统筹全局 |
| 交互设计师 | 毕加索 | `picasso-interaction-designer` | 设计页面结构、流程和交互说明 |
| 研发工程师 | 图灵 | `turing-frontend-engineer` | 前端页面和组件实现 |
| 测试工程师 | 福尔摩斯 | `holmes-qa-reviewer` | 测试验收，输出问题清单和风险报告 |

---

## 三、每个角色的职责

### 乔布斯（产品负责人）

**负责：**
- 接收你的需求描述，提问补全细节
- 整理成完整的产品需求文档（背景、目标、流程、字段、状态、权限、验收标准）
- 判断需要召唤毕加索、图灵还是福尔摩斯
- 在所有工作完成后，汇总整个需求的完成情况

**不做：** 直接写代码（除非你明确要求）

---

### 毕加索（交互设计师）

**负责：**
- 接收乔布斯的需求文档
- 设计每个页面的结构、信息架构、操作清单
- 覆盖所有状态（加载、空态、错误、无权限、成功反馈等）
- 说明复杂交互的具体逻辑
- 给出组件复用建议和研发注意事项

**不做：** 改业务目标、直接写代码

---

### 图灵（研发工程师）

**负责：**
- 接收需求文档和交互说明，进行前端实现
- 优先复用已有组件和设计 Token
- 实现后输出变更报告（改了哪些文件、实现了什么、如何验证）

**不做：** 擅自改数据库、接口、权限、全局配置（必须先报告）

---

### 福尔摩斯（测试工程师）

**负责：**
- 根据需求文档和交互说明验收图灵的实现
- 检查主流程、异常、边界状态、权限、表单校验
- 重点排查图灵是否有超出范围的改动
- 输出测试报告，说明是否可以进入下一阶段

**不做：** 直接改代码（除非你明确要求）

---

## 四、推荐使用流程

```
你 → 乔布斯 → 毕加索 → 乔布斯确认 → 图灵 → 福尔摩斯 → 乔布斯汇总
```

**详细步骤：**

1. **你**：向乔布斯描述需求（可以很模糊）
2. **乔布斯**：提问补全细节，整理产品需求文档
3. **你**：确认需求文档是否正确
4. **乔布斯**：判断是否需要交互设计，召唤毕加索
5. **毕加索**：输出页面结构和交互说明
6. **乔布斯**：检查交互方案是否符合需求
7. **你**：确认交互方案
8. **乔布斯**：召唤图灵，附上需求文档和交互说明
9. **图灵**：实现前端功能，输出变更报告
10. **福尔摩斯**：验收测试，输出测试报告
11. **乔布斯**：汇总整个需求的完成情况

## 六、注意事项

1. **先找乔布斯，不要直接找图灵。** 需求没整理清楚就开始写代码，最容易返工。

2. **交互说明是图灵的工作依据。** 没有毕加索的交互说明就让图灵开始写代码，等于让他自己猜，结果很可能跟你想的不一样。

3. **图灵有改动限制。** 如果图灵说某个操作需要申请确认（比如改数据库结构），这是为了保护你的项目，不要绕过它。

4. **福尔摩斯不改代码。** 他只发现问题，不解决问题。发现问题后，让图灵来修复。

5. **每个角色都会问问题。** 这是正常的，比一言不发就开始工作要好得多。遇到「待确认项」，及时给出答案。

6. **已有设计规范要遵守。** 这个项目有完整的设计系统文档（`docs/`），所有 Skill 都会优先复用它，不要让他们绕过。

---

## 七、不应该怎么用

| 错误做法 | 正确做法 |
|---------|---------|
| 直接找图灵「帮我做个页面」 | 先找乔布斯整理需求，再让毕加索设计，再找图灵实现 |
| 跳过毕加索直接让图灵自己决定页面怎么设计 | 涉及新页面或复杂交互，必须先经过毕加索 |
| 让图灵擅自改数据库或接口 | 必须先让图灵列出变更申请，你确认后才能改 |
| 直接让福尔摩斯改代码 | 福尔摩斯只发现问题，修复要交给图灵 |
| 跳过乔布斯的最终汇总 | 每次需求完成后，让乔布斯做一次汇总，留档备查 |
| 不给角色传上下文就激活 | 每次切换角色时，把上一个角色的输出粘贴进来 |

## 八、完整示例

### 场景：我想做一个「课程发布」功能

---

**第一步：找乔布斯描述需求**

```
/jobs-product-owner

我想在平台里加一个课程发布功能。老师编辑好课程后，可以点一个「发布」按钮，
课程就变成已发布状态，学生就能看到了。
```

**乔布斯会输出：**
- 补充提问（发布前要审核吗？可以撤销发布吗？谁有权限发布？）
- 产品需求文档（需求背景、主流程、异常流程、状态说明、权限规则、验收标准）

---

**第二步：找毕加索设计交互**

```
/picasso-interaction-designer

请根据以下需求文档，设计课程发布功能的交互说明：
[粘贴乔布斯的需求文档]
```

**毕加索会输出：**
- 发布按钮的位置和状态（正常/加载/禁用/成功）
- 发布前的二次确认弹窗设计
- 发布成功/失败的反馈方式
- 状态流转的视觉表达方式

---

**第三步：乔布斯确认交互方案**

```
/jobs-product-owner

毕加索输出了交互说明，请你检查是否符合需求文档：
[粘贴毕加索的交互说明]
```

---

**第四步：找图灵实现**

```
/turing-frontend-engineer

请根据以下需求文档和交互说明，实现课程发布功能：
[粘贴需求文档]
[粘贴交互说明]
```

**图灵会：**
1. 先输出实现计划（修改哪些文件、复用哪些组件）
2. 等你确认后再开始写代码
3. 完成后输出变更报告

---

**第五步：找福尔摩斯验收**

```
/holmes-qa-reviewer

请对课程发布功能进行验收测试：
[粘贴需求文档]
[粘贴交互说明]
[粘贴图灵的变更报告]
```

**福尔摩斯会输出：**
- 测试用例列表
- 通过项、问题项、风险项
- 是否可以上线的结论

---

**第六步：乔布斯最终汇总**

```
/jobs-product-owner

请汇总课程发布功能的完成情况：
[粘贴图灵的变更报告]
[粘贴福尔摩斯的测试报告]
```

---

这就是一次完整的产研流程。
